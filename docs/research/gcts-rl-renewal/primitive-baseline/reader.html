\[a=b,\;b=c,\;c=d\;\vdash\;a+0=b.\]

The already admitted static catalog contains \(119633\) primitive recipes and \(113406\) formulas, with \(24\) required proof rows. The baseline starts with \(0\) stored lemma bodies. Its declared search limits are \(128\) attempts, \(20\,\mathrm{s}\) of search and \(2000\) trace events. None of these inputs supplies a proof sequence.

The same symbolic point model enforces occupancy and agreement of nearby and distant markings. Validity comes from the licensed inference steps and the final independent symbolic and point certificate. This is a finite ground calculus; it does not yet provide a complete Peano arithmetic or Hilbert geometry prover, or a universal finite Wang compiler.

Post-failure inspection finds a concrete admission blocker.

The platform metadata requires the current owner’s independent review file. That exact file is missing from the worker’s frozen input manifest, although it is present in the parent owner’s manifest. The worker’s source explicitly authenticates the required file and then rejects any required input absent from its own manifest. These literal inputs therefore cannot pass that admission gate.

ROOT and the source author independently identify this contradiction using source and metadata inspection. The earlier prospective claim that every required worker input was present was mistaken and is withdrawn. Correct raw hashes for the entries that are listed do not establish a complete list.

This is a deterministic source/plan finding consistent with the observed failure. It does not recover the suppressed runtime exception or reveal a saved search phase. The original failed attempt remains UNKNOWN; no preflight or scientific search is rerun to diagnose it.

Three roles produce different kinds of progress.

Proof discovery

The original full-inventory baseline reaches its first actual invocation. The coordinator records its failure without inserting a proof, trimming the catalog, enlarging the budget or relabeling the outcome.

Engine development

A new read-only API constructs a candidate’s key, point values, command and identity in one uninterrupted guarded read step. It repeats the full integrity check before every advance, including EOF, and returns detached records.

Its intended benefit is less repeated validation. The complete literal comparator and existing controls remain in the source. No new API test or speed measurement has run.

Independent review

Separate reviewers catch a child deadline mismatch and then a missing exact input pin before baseline execution. The corrected plans pass prospective review, but that review misses a second required worker input. Post-failure inspection exposes the omission, and the completeness claim is withdrawn. Actual failure records are reviewed separately.

The new API also receives a different-person source review. Earlier authorship of borrowed components is disclosed; these reviews do not independently reimplement the whole engine.

The candidate API adds \(23\) declared mutation, stale-stream and output-detachment controls per synthetic case. All \(12\) original cases, \(24\) rows, \(7\) authored groups, \(31\) feature meanings and full \(64/65\) capacity controls remain. The \(276\) new controls are source declarations only until a whole owned test finishes.

This supports parallel engineering and independent checking. It adds no new theorem, learned policy, lemma-transfer result or advantage over another prover.

The next experiments address concrete obstacles.

First, retain a bounded diagnostic for any worker exception in a new reviewed source version, and derive the complete manifest by traversing every required metadata object. This must include the newly found missing review file. The current failure remains immutable. The correction must preserve the original declaration, rules and budgets.

Separately, complete the candidate API’s unchanged whole synthetic test before using it as authority for lemma search or learning. Then automatically found proof fragments can populate the reusable lemma inventory, and the same complete primitive fallback can be compared with fixed, uniform and learned proposals on arithmetic and symbolic Hilbert targets.

That comparison must charge preparation, mining, training, search and checking costs. A shared primitive kernel, genuine held-out targets and checked returned proofs are needed before a GCTS or RL advantage can be assessed. The broader research goals remain active.

Reproducibility and scope.

The actual baseline retains the original \(170\,\mathrm{s}\) cold-child, \(175\,\mathrm{s}\) owner and \(180\,\mathrm{s}\) caller limits, and \(512\,\mathrm{MiB}\) memory envelope with the prospective conditional \(32\,\mathrm{MiB}\) postlude reserve. The installed Darwin runtime has earlier finite unit evidence; the published kernel-source version does not exactly match the running kernel. No universal OS, hard-cap, whole-host or arbitrary cleanup guarantee follows.

The closed failure has no accepted resource gate. No final metadata adapter is invoked on that known failed gate. The subsequent raw metadata reconciliation is additional work. Full chronological search replay, RNG and reward replay, learning, production cluster qualification and a universal compiler remain unqualified.
